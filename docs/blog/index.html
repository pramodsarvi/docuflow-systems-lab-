Summary

docuflow reads scanned documents (printed and handwritten) with a vision model, indexes them in Postgres + pgvector, and answers questions with an agent loop, while ingestion keeps running. Everything runs on Kubernetes: one machine, one NVIDIA L40S (46 GB), a kind cluster, and three vLLM servers sharing that GPU.

Almost everything scales on queue depth, through KEDA, which turns each signal into a Kubernetes HPA:

What scales Signal Scaler Range
ingest workers (io, vlm, embed) work tokens waiting in a RabbitMQ queue, plus jobs running KEDA rabbitmq + postgresql 0 to N, scale to zero
API CPU, plus interactive queries in flight KEDA cpu + postgresql 1 to 8
vLLM page reader and embedder vLLM's own running + waiting requests KEDA prometheus 1 to 2 (local), 1 to 4 (prod)

What the stress tests showed:

  • Queue-driven scale-out works, and is fast. From zero, KEDA had the first page-reading worker up in 10 s and 6 of them in 30 s. Under an 800-page burst with 12 query clients the system answered 1,635 queries with zero errors while ingesting 34 pages/min.
  • Most of the bugs weren't in the autoscaler. They sat around it: an in-app concurrency cap that left 4 of 12 new pods idle, HTTP keep-alive pinning every worker to the first vLLM replica, kubectl apply resetting KEDA's replica counts, KEDA failing to resolve short DNS names, and rolling updates that deadlocked on GPU memory. Fixing them took ingest from 34 to ~170 pages/min on the same GPU.
  • Scaling the wrong tier does nothing. KEDA scaled the API to 8 pods under 96 concurrent queries; each pod used 5 millicores, because the bottleneck was the agent model's batch slots (32 running, 64 waiting). Latency only moved when the model server got more capacity.
  • On one GPU, the GPU is the ceiling. Autoscaling redistributes a fixed budget. The last lever was choosing what the budget is for: an ingest mode that pauses queries and gives the whole GPU to page reading.

Part 1

The system and why it scales on queues

What docuflow does

docuflow ingests scanned documents that mix printed text and handwriting, then answers questions about them. Ingest and querying happen at the same time: a page becomes searchable seconds after it is read, and a question asked mid-ingest sees whatever has been indexed so far.

A page moves through three stages, each a job in its own lane:

Lane Stage What it does Cost
io fetch stream a slice of 20 pages from a dataset, store each image, enqueue one extract job per page network, CPU
vlm extract the vision model reads the page: every region's text, tagged printed/handwritten and a role GPU, 3 to 25 s
embed embed embed the page's chunks, mark the page indexed GPU, under 0.1 s

Questions go to an agent loop: a small LLM chooses actions (search, get_page, read_page_image, answer) over hybrid vector + full-text search until it can answer with citations.

 POST /ingest ─► fetch (io lane) ─► extract (vlm lane) ─► embed (embed lane) ─► pgvector + tsvector
 POST /query  ─► api ─► agent loop ─► model-llm (+ search, + model-vlm for page re-reads)

  ┌─ RabbitMQ ──────────────┐     ┌─ GPU node (1x L40S, time-sliced) ──────────────┐
  │ docuflow.io     tokens  │     │ model-vlm    Qwen2.5-VL-3B     KEDA 1..N        │
  │ docuflow.vlm    tokens  │──►  │ model-llm    Qwen3-4B          agent            │
  │ docuflow.embed  tokens  │     │ model-embed  Qwen3-Embedding   KEDA 1..N        │
  └─────────────────────────┘     └─────────────────────────────────────────────────┘
        ▲ KEDA reads queue length          ▲ KEDA reads vLLM metrics via Prometheus
        │                                  │
  worker-io / worker-vlm / worker-embed  (CPU pods, 0..N each)    api (1..8)

Every component is a container on Kubernetes: - the API - the workers, one Deployment per lane - three vLLM servers, one per model - RabbitMQ - Postgres

The workers don't request a GPU. They're HTTP clients of the vLLM servers, and vLLM batches their concurrent requests on the GPU.

Three workloads, three shapes of load

The system serves three very different kinds of demand, and each needs its own scaling signal:

  1. Batch ingest arrives in bursts: one POST /ingest can enqueue 5,000 pages in a second. The demand is the backlog: how many pages are waiting. CPU on the worker pods says almost nothing about it, because a worker spends nearly all its time waiting on a model server.
  2. Interactive queries arrive continuously and care about latency. The demand is concurrency: how many questions are being answered right now.
  3. Model inference is shared by both. The demand is what the model server itself reports: requests running in its batch, and requests waiting for a slot.

Why not scale on CPU

The classic Horizontal Pod Autoscaler scales on CPU or memory utilisation. For this system that signal is wrong in both directions:

  • A page-reading worker sends one request to vLLM and waits 3 to 25 s for the answer. Its CPU is near zero whether 5 pages are queued or 5,000.
  • An API pod running 12 agent loops is also near zero: during the stress test, 8 API pods each used 5 millicores while 96 queries were in flight.
  • With no work, CPU-based HPA still keeps minReplicas (at least 1) running. A queue-based scaler can go to zero.

Queue depth measures the actual demand, it's known before any pod starts working, and it reaches zero when the work is done. That's the signal KEDA is built around, and Part 2 describes how it plugs into the HPA.

Where the GPU fits

There is one GPU. Every replica of every model server gets a time-slice of it and a fixed share of its 46 GB of memory. So autoscaling here redistributes a fixed budget between: - page reading (ingest) - the agent model (query latency) - embeddings (both)

That constraint drives several of the failures in Part 7 and the "ingest mode" at the end of Part 6.

Part 2

HPA and KEDA, precisely

KEDA is often described as "an alternative to the HPA". It isn't one: KEDA creates and drives an HPA. Knowing exactly what each component does explains every scaling behaviour in the later parts.

The HPA on its own

The Horizontal Pod Autoscaler is a control loop in kube-controller-manager. Every 15 s it reads a metric for a target (Deployment or StatefulSet) and computes:

desiredReplicas = ceil( currentReplicas × currentMetricValue / targetMetricValue )

For external metrics with an AverageValue target, the form KEDA uses, currentMetricValue is already the total divided by current replicas, so this reduces to:

desiredReplicas = ceil( totalMetricValue / targetPerPod )

A few properties matter in practice:

  • It never goes below minReplicas, and minReplicas must be at least 1. The HPA cannot scale to zero.
  • With several metrics, it computes a desired count for each and takes the maximum.
  • It ignores changes within a 10% tolerance.
  • behavior.scaleUp / behavior.scaleDown set stabilisation windows and rate limits (for example "add at most 3 pods per 10 s").
  • Out of the box it can read only resource metrics (CPU, memory) through metrics-server. Anything else needs an adapter that serves the external.metrics.k8s.io API.

What KEDA adds

KEDA runs two components:

  • The operator watches ScaledObject resources. For each one it creates an HPA named keda-hpa-<name>, and it owns the 0 ↔ 1 transition, which the HPA cannot do.
  • The metrics server implements external.metrics.k8s.io. When the HPA asks for a metric, KEDA's metrics server runs the scaler, for example a RabbitMQ queue-length check or a SQL query, and returns the number.

So responsibility is split by range:

Transition Who does it Driven by
0 → 1 (activation) KEDA operator any trigger above its activationValue, checked every pollingInterval
1 → N and N → 1 the HPA KEDA created ceil(metric / target), max over triggers, behavior policies
1 → 0 (deactivation) KEDA operator all triggers at or below activation for cooldownPeriod seconds

A minimal example from this project. The page-reading workers scale on a RabbitMQ queue:

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: worker-vlm}
spec:
  scaleTargetRef: {name: worker-vlm}     # the Deployment
  minReplicaCount: 0                     # KEDA may scale it to zero
  maxReplicaCount: 24
  pollingInterval: 5                     # activation check every 5 s
  cooldownPeriod: 60                     # 60 s with nothing to do -> scale to zero
  triggers:
    - type: rabbitmq
      authenticationRef: {name: docuflow-rabbitmq}
      metadata: {protocol: amqp, queueName: docuflow.vlm, mode: QueueLength, value: "2"}

With 300 tokens in docuflow.vlm and value: "2", the HPA wants ceil(300 / 2) = 150 replicas, capped at maxReplicaCount: 24. With 5 tokens it wants 3. With 0 tokens for 60 s, the operator scales the Deployment to zero.

The knobs, and what each one actually controls

Field Controls Common mistake
value / targetQueryValue / threshold work per replica in steady state treating it as a global threshold; it is per pod
activationValue when to go 0 → 1 leaving it unset on a scaler whose default activation is high
pollingInterval how often KEDA checks activation expecting it to also speed up 1 → N (the HPA's 15 s loop does that)
cooldownPeriod delay before scaling to zero only expecting it to slow down N → 1 (use behavior.scaleDown)
advanced.horizontalPodAutoscalerConfig.behavior HPA rate limits and stabilisation none: this is the right tool for N → 1 damping
minReplicaCount / maxReplicaCount bounds a max that the app can't actually use (Part 7, failure 1)

Multiple triggers

When a ScaledObject has several triggers, the HPA takes the maximum desired count across them. This project relies on that twice:

  • Workers pair a backlog trigger (RabbitMQ queue length) with a running trigger (Postgres count of running jobs, target 1). When the queue empties, the backlog trigger drops to zero but the running trigger still asks for one pod per in-flight job, so KEDA never scales away a worker in the middle of a 20 s page read.
  • The API pairs cpu (the classic HPA metric) with "queries in flight": whichever is under more pressure wins.

Authentication

Scaler credentials should live in a Secret, referenced by a TriggerAuthentication, never inlined in the ScaledObject:

apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata: {name: docuflow-rabbitmq}
spec:
  secretTargetRef:
    - {parameter: host, name: docuflow-secrets, key: RABBITMQ_URL}

One consequence is easy to miss: KEDA connects from its own namespace. amqp://rabbitmq:5672 resolves inside docuflow but not inside keda. Use fully qualified service names in any URL a scaler reads (Part 7, failure 6).

Seeing what KEDA decided

kubectl -n docuflow get scaledobject                # READY / ACTIVE per ScaledObject
kubectl -n docuflow get hpa                         # the HPAs KEDA created, with current/target metric values
kubectl -n docuflow describe hpa keda-hpa-worker-vlm
kubectl -n keda logs deploy/keda-operator | grep ERROR

The HPA's TARGETS column shows the live per-pod value against the target. For example, 25667m/4 (avg) means 25.7 queries in flight per API pod against a target of 4, which is why that HPA was scaling up.

Part 3

The queue: RabbitMQ tokens, Postgres truth

The starting point

The first version of docuflow used Postgres as the job queue: workers claimed rows with SELECT ... FOR UPDATE SKIP LOCKED, and KEDA's postgresql scaler ran a count(*) on the jobs table. That works and is a perfectly good design. The move to RabbitMQ came from two concerns:

  • Polling load. Every idle worker polls the database twice a second. Fifty idle workers add up to 100 queries per second that do nothing.
  • A standard scaling signal. Queue length on a broker is what KEDA, dashboards and operators expect to see, and it's cheap for KEDA to read.

Why not move the jobs into RabbitMQ entirely

The jobs table holds more than a FIFO can express. At claim time, the app applies workload rules:

  • priority, with downstream stages first, so a page that's already been read gets embedded before a new page is read, and becomes queryable sooner
  • fair share across datasets: a 5,000-page dataset can't starve a 50-page one
  • pause and resume a lane or a dataset
  • leases and retries: a job whose worker died is requeued when its lease expires; a job that keeps failing is parked as dead for inspection

Moving all of that into broker features (priority queues, per-dataset queues, consumer-side limits) means re-building it in a place that's harder to query and test. So the design keeps Postgres as the source of truth and makes RabbitMQ carry work tokens.

Tokens

There's one durable queue per lane: docuflow.io, docuflow.vlm, docuflow.embed. Each runnable job is represented by one message, the token, with no payload.

enqueue job  ──► INSERT INTO jobs ... COMMIT ──► publish 1 token to docuflow.<lane>
worker loop  ──► basic_get token ──► claim best eligible job in Postgres (rules applied here)
                  ├─ got a job        ─► ack token, run the job (lease + retries tracked in Postgres)
                  ├─ nothing runnable ─► ack token (surplus: duplicate, or the dataset is paused)
                  └─ runnable but held back (lane limit, query back-off) ─► nack + requeue, sleep 1 s

The worker side, from docuflow/worker.py:

tag = broker.take(lane)                 # basic_get, manual ack
if tag is None:
    time.sleep(0.5); return None
job = jobs.claim(lane, name)            # FOR UPDATE SKIP LOCKED + priority, fair share, pause, limits
if job:
    broker.done(tag)                    # the job row now tracks the work
    return job
if broker.runnable(lane) == 0:
    broker.done(tag)                    # surplus token: drop it
else:
    broker.give_back(tag); time.sleep(1)

Three details keep this correct:

  1. Publish after commit. A token published inside the transaction can reach a worker before the row is visible; the worker would then find nothing to claim and drop the token. Callers that enqueue inside a transaction call jobs.notify_after(stage, n) once it has committed.
  2. Ack early. The token is acknowledged as soon as the job is claimed, not when the job finishes. A page read can take 25 s and an embedding call milliseconds; holding unacked messages across long jobs ties tokens to broker connections and heartbeats. Once claimed, the Postgres lease covers the job, and lease expiry republishes a token if the worker dies.
  3. Paused work releases pods. A token for a paused dataset is dropped (nothing is runnable), so the queue shrinks and KEDA scales the workers down. On resume the reconciler (below) restores the tokens.

Retries with backoff: delay queues

A failed job goes back to queued in Postgres with run_after = now() + backoff (5 s, 10 s, 20 s… up to 300 s). Its token goes to docuflow.<lane>.delay, a queue with no consumers whose dead-letter target is the lane queue:

ch.queue_declare("docuflow.vlm.delay", durable=True, arguments={
    "x-dead-letter-exchange": "", "x-dead-letter-routing-key": "docuflow.vlm"})
ch.basic_publish("", "docuflow.vlm.delay", b"1", pika.BasicProperties(delivery_mode=2, expiration="20000"))

When the per-message TTL expires, RabbitMQ moves the token to docuflow.vlm, exactly when the job becomes runnable again. KEDA reads only the lane queue, so backing-off jobs don't keep pods alive.

Reconciliation

Tokens can be lost: a publish can fail after a commit, or the broker can restart without persistence. Every worker runs a reconciler every 30 s, single-flight across all workers through a Postgres advisory lock:

def reconcile(lane):
    with db.pool().connection() as c:
        if not c.execute("SELECT pg_try_advisory_xact_lock(hashtext('reconcile:' || %s)) ok", (lane,)).fetchone()["ok"]:
            return 0
        missing = runnable(lane) - depth(lane)          # runnable jobs in Postgres minus tokens in the queue
        return notify(lane, missing) if missing > 0 else 0

Over-publishing is harmless (surplus tokens are dropped at claim time), so the reconciler only ever adds tokens.

The scaling signal this produces

For KEDA, the lane queue length is now "runnable jobs not yet claimed". It excludes jobs in backoff, jobs that are paused, and jobs already running. That's exactly the backlog a new pod could start on. Running jobs are covered by the second trigger (Part 4). With RABBITMQ_URL unset, workers fall back to polling Postgres, which keeps unit tests and single-machine development simple.

Tested against a real broker

tests/test_broker.py runs against a real RabbitMQ and checks four behaviours: - one ingest publishes exactly one token per fetch job, after commit - a worker consumes exactly one token per claimed job - surplus and paused tokens are dropped, and the reconciler restores them on resume - a failed job's token reappears on the lane queue only after its backoff

Part 4

Every ScaledObject, explained

The full manifests are in k8s/base/keda.yaml and k8s/components/models/autoscaling.yaml. This part shows the final versions and the reasoning behind each number.

Workers: backlog plus running

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: worker-vlm}
spec:
  scaleTargetRef: {name: worker-vlm}
  minReplicaCount: 0
  maxReplicaCount: 24
  pollingInterval: 5
  cooldownPeriod: 60
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp: {stabilizationWindowSeconds: 0, policies: [{type: Pods, value: 3, periodSeconds: 10}]}
        scaleDown: {stabilizationWindowSeconds: 30, policies: [{type: Pods, value: 1, periodSeconds: 20}]}
  triggers:
    - type: rabbitmq                       # backlog: tokens waiting = runnable, unclaimed jobs
      name: vlm-queue
      authenticationRef: {name: docuflow-rabbitmq}
      metadata: {protocol: amqp, queueName: docuflow.vlm, mode: QueueLength, value: "2", activationValue: "0"}
    - type: postgresql                     # in progress: never scale away a pod mid-job
      name: vlm-running
      authenticationRef: {name: docuflow-pg}
      metadata:
        query: "SELECT count(*) FROM jobs WHERE lane='vlm' AND status='running'"
        targetQueryValue: "1"
        activationTargetQueryValue: "0"
  • value: "2": two waiting pages per worker. Each worker handles one page at a time, so a target of 2 makes the backlog clear in two rounds while bursts still scale out fast.
  • maxReplicaCount: 24: about the number of concurrent page reads that two vLLM replicas (16 batch slots each) can keep busy. Workers beyond that only lengthen vLLM's internal queue.
  • Fast up, slow down: add up to 3 pods per 10 s, remove 1 per 20 s. Scale-up latency matters for a burst; scale-down flapping wastes pod starts.
  • terminationGracePeriodSeconds: 180 on the Deployment: on scale-down, a worker gets SIGTERM, finishes its current page and exits. Anything cut off is requeued by lease expiry.

worker-io (target 2, max 3) and worker-embed (target 8, max 3) follow the same pattern. Embedding is a ~0.1 s call, so one worker clears many tokens per second and the target is higher.

API: CPU and concurrency

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: api}
spec:
  scaleTargetRef: {name: api}
  minReplicaCount: 1
  maxReplicaCount: 8
  triggers:
    - type: cpu                            # the classic HPA metric
      metricType: Utilization
      metadata: {value: "60"}
    - type: postgresql                     # interactive queries currently in flight
      authenticationRef: {name: docuflow-pg}
      metadata:
        query: "SELECT count(*) FROM inflight WHERE beat > now() - interval '120 seconds'"
        targetQueryValue: "4"

Each agent query registers itself in an inflight table and heartbeats it between steps. The 120 s window means a crashed query stops counting quickly. A cpu trigger needs CPU requests on the pod and can't scale to zero, so minReplicaCount is 1.

This is the ScaledObject that taught the most (Part 7, failure 9). It scaled correctly, to 8 pods under 96 concurrent queries, and latency didn't improve at all, because the API wasn't the bottleneck.

vLLM servers: scale on the model server's own queue

vLLM exposes vllm:num_requests_running (sequences in the current batch) and vllm:num_requests_waiting (requests queued for a batch slot). Prometheus scrapes them through a PodMonitor, and KEDA reads them with the prometheus scaler:

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: model-vlm}
spec:
  scaleTargetRef: {name: model-vlm}
  minReplicaCount: 1
  maxReplicaCount: 2                       # 4 in prod (whole GPUs)
  pollingInterval: 15
  cooldownPeriod: 300                      # a model server takes ~1 min to start: don't flap
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp: {stabilizationWindowSeconds: 30, policies: [{type: Pods, value: 1, periodSeconds: 60}]}
        scaleDown: {stabilizationWindowSeconds: 300, policies: [{type: Pods, value: 1, periodSeconds: 120}]}
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://kube-prometheus-stack-prometheus.monitoring.svc:9090
        query: >-
          sum(vllm:num_requests_running{namespace="docuflow", pod=~"model-vlm-.*"})
          + sum(vllm:num_requests_waiting{namespace="docuflow", pod=~"model-vlm-.*"}) or vector(0)
        threshold: "4"
  • Running + waiting, not waiting alone. Waiting is zero until the batch is full, and by then latency is already hurting. Running + waiting measures total demand on the server.
  • The threshold must be reachable. The first version used 6 per replica with at most 6 workers sending requests: total demand could never exceed 6, so the second replica never started (Part 7, failure 2).
  • or vector(0) makes the query return 0 instead of "no data" when no pod is up yet.
  • The embedding server (model-embed) uses the same trigger with threshold 8. The agent model (model-llm) gets the same treatment in prod (threshold 96 against 128 batch slots on a whole GPU). Locally one GPU can't hold a second copy of it next to the others.

Two chains of scaling

Put together, demand flows through two autoscaling layers:

ingest burst ─► RabbitMQ tokens ─► KEDA ─► worker-vlm pods ─► concurrent requests ─► vLLM running+waiting
                                                                                     ─► KEDA ─► model-vlm replicas
query burst  ─► inflight rows ─► KEDA ─► api pods ─► agent requests ─► model-llm queue (─► KEDA in prod)

The worker layer converts backlog into concurrency, and the model layer converts concurrency into GPU replicas. Each layer's maximum has to be sized against the next layer's capacity. Mismatches between them caused failures 1, 2 and 9 in Part 7.

Part 5

GPUs: one L40S, three vLLM servers

Getting a real GPU into kind

kind runs Kubernetes nodes as Docker containers, so the GPU has to pass through two container layers: host Docker into the node container, then the node's containerd into the pods.

On the host, make the NVIDIA runtime Docker's default, and let it select GPUs through a volume mount (kind can mount files but can't pass --gpus):

sudo nvidia-ctk runtime configure --runtime=docker --set-as-default
sudo nvidia-ctk config --set accept-nvidia-visible-devices-as-volume-mounts=true --in-place
sudo systemctl restart docker

In the kind config, mounting /dev/null at a magic path asks the toolkit to inject every GPU into that node only:

- role: worker
  labels: {docuflow.io/pool: gpu}
  extraMounts:
    - {hostPath: /dev/null, containerPath: /var/run/nvidia-container-devices/all}
    - {hostPath: /var/cache/docuflow-hf, containerPath: /var/cache/docuflow-hf}   # model weights survive rebuilds

Inside the GPU node (scripts/cluster-up.sh does this for you): 1. Install nvidia-container-toolkit and make it containerd's default runtime. 2. Unmount the masked /proc/driver/nvidia/params. The host toolkit masks it, and without it NVML fails in nested containers with driverInitFileInfo ... result=11. 3. Restart containerd. 4. Taint the node (nvidia.com/gpu=present:NoSchedule) so only GPU workloads land on it. 5. Label it nvidia.com/gpu.present=true. The device-plugin chart only schedules onto nodes that Node Feature Discovery has labelled.

Two host settings caught us here: - kind runs several kubelets on one kernel, so the default inotify limits run out. The device plugin then crashes with too many open files. Raise fs.inotify.max_user_instances to 8192. - Newer vLLM images are built for CUDA 13 and crash at import (libnvrtc.so.13) on a 570 driver. v0.13.0 (CUDA 12.9) runs on it.

Sharing one GPU: time-slicing

The NVIDIA device plugin with time-slicing advertises one physical GPU as several nvidia.com/gpu units:

config:
  map:
    default: |-
      version: v1
      sharing:
        timeSlicing:
          resources: [{name: nvidia.com/gpu, replicas: 6}]

The node then shows nvidia.com/gpu: 6, and each vLLM pod requests 1. Time-slicing shares compute by context switching, but memory isn't isolated: every process sees all 46 GB, and nothing stops one from taking it all. The budget has to be enforced by the servers themselves.

The memory budget

vLLM normally sizes itself with --gpu-memory-utilization (a fraction of total memory) and works out how much KV cache fits by profiling at startup. With several servers on one GPU, that profiling goes wrong. When we started all three at once, the agent model measured the other servers' memory as its own usage and failed:

Available KV cache memory: -12.92 GiB
EngineCore failed to start.

The fix is to give each server a fixed KV cache with --kv-cache-memory-bytes. Then startup no longer depends on what the other servers are doing at that moment. --gpu-memory-utilization remains as an upper bound that vLLM checks against free memory at startup.

Budgets, as measured and then right-sized:

Server Model Weights KV cache Batch slots Approx. footprint
model-vlm (x1..2, x3 in ingest mode) Qwen2.5-VL-3B 7.5 GB 3 → 1.5 GiB (only 12–15% was used) 16 ~10 GB each
model-llm Qwen3-4B-Instruct 7.6 GB 4 → 8 GiB (81% used at 32 sequences) 32 → 64 ~17 GB
model-embed (x1..2) Qwen3-Embedding-0.6B 1.2 GB 1 GiB → 512 MiB 64 ~2.5 GB each

Measured totals: the first three servers together used 27 GB. With a second page reader it was 37–38 GB, and after the agent model's KV increase 43.7 GB of 46. That was too full to start a second embedding server, which is why the page-reader KV cache was cut to what it actually used.

The embedding server needed one more fix. With --max-model-len 8192 it refused to start with a 512 MiB cache ("0.88 GiB KV cache is needed"). Chunks are at most 700 characters, so --max-model-len 2048 is plenty.

Rolling updates deadlock on a shared GPU

A Deployment's default RollingUpdate starts the new pod before stopping the old one. On a full GPU, the new pod can't get memory and fails its startup check:

ValueError: Free memory on device (1.2/44.4 GiB) on startup is less than desired GPU memory utilization (0.06, 2.66 GiB)

It crash-loops, and the old pod stays up because the new one never becomes ready. On a shared GPU, model servers use strategy: Recreate. That affects only updates (image, flags), not KEDA scaling. The prod overlay, with one whole GPU per replica, patches it back to RollingUpdate with maxSurge: 1.

Workers don't touch the GPU

docuflow's workers request no GPU. A page-reading worker is an HTTP client: it sends a page to model-vlm and waits. This split is what makes queue-based scaling work with GPUs: - Worker pods are cheap and fast to start (about 2 s), so KEDA can scale them from 0 to 48 freely. - Model servers are expensive and slow to start (1–2 minutes, about 10 GB of GPU memory each), so they scale conservatively, on their own queue, with long cooldowns. - vLLM's continuous batching turns N concurrent worker requests into one batched GPU pass. More workers means more throughput, up to the server's batch slots.

When one GPU isn't enough

Autoscaling on one GPU only redistributes a fixed budget. At the end of the stress tests the GPU was at 100% compute, 309 of 350 W, and 43.7 of 46 GB. Throughput beyond that needs more GPUs. The prod overlay gives each model server whole GPUs, lets KEDA scale model-vlm and model-llm to 4 replicas each, and lets the GPU node pool's cluster autoscaler add machines. When another GPU is too expensive, the remaining lever is deciding what the GPU is for at a given time, the ingest mode in Part 6.

Stress testing: method and results

The load generator

scripts/stress.py produces both kinds of load at once and samples the cluster while it runs:

  1. Ingest: one POST /ingest of N pages in vlm mode, so the vision model really reads every page. The synthetic dataset generates forms locally, with known field values.
  2. Queries: C closed-loop clients, each sending a question, waiting for the answer, and repeating. Questions are generated from the synthetic forms ("Who signed document INV-1005?"), so answers can be checked for correctness, not just for HTTP 200. --query-steps 8,24,48 ramps the client count every --step-seconds.
  3. Sampling, every 10 s: - replicas (ready/desired) for every Deployment - pending pods - RabbitMQ depth per lane - jobs queued/running per lane - pages indexed - queries in flight - GPU utilisation and memory
  4. Scale-down phase: with --observe-after, it stops all load and keeps sampling, so the report also shows KEDA scaling back down.
  5. Report: a markdown file with ingest throughput, query latency per load step (p50/p95/max), error rate, answer correctness, peak replicas, and the full timeline.
python scripts/stress.py --api http://docuflow.localtest.me --dataset synthetic --pages 2000 --offset 2000 \

Part 7

What broke, and the fixes

Ten failures from building and stress-testing the system. Most of them sat around the autoscaler rather than in it, and none showed up in unit tests or a quiet cluster.

1. KEDA started pods that sat idle

Symptom. 12 page-reading workers were running, but only 8 jobs were. The database showed vlm running = 8 no matter how many pods KEDA added.

Cause. The app enforces its own concurrency rules at claim time, including a per-dataset cap for fair share (PER_DATASET_CAP=8). With a single dataset being ingested, the cap allowed only 8 running jobs. KEDA's maximum had been raised to 12 without raising the cap, so 4 pods polled forever.

Fix. On Kubernetes the pod count is the real limit, so every in-app limit must sit above KEDA's maxReplicaCount. The config now says so next to the values. Ingest went from 39.7 to 56.5 pages/min.

General lesson. Any limit inside the app (connection pools, semaphores, per-tenant caps, broker prefetch) is a second autoscaling ceiling. KEDA can't see it.

2. A scaling threshold that could never be reached

Symptom. model-vlm stayed at 1 replica through a whole run with a backlog of 700 pages.

Cause. Its trigger was "running + waiting requests, 6 per replica", and at most 6 workers sent requests. Total demand could never exceed 6, so the desired count was always ceil(6/6) = 1. The prod overlay had the same flaw at larger numbers: a threshold of 48 with 24 workers.

Fix. Size thresholds across layers: the upstream layer's maximum concurrency must be able to exceed the downstream threshold. Workers went to 24, the threshold to 4. The second replica started within a minute.

3. A new replica that got no traffic

Symptom. After KEDA added a second vLLM page-reading server, replica A showed 16 running + 6 waiting; replica B showed 2 running.

Cause. A Kubernetes Service balances per connection (kube-proxy picks a backend when a TCP connection opens). The workers' HTTP client kept connections alive, so every worker stayed on whichever replica it had first reached, and that was the only replica that existed when they started.

Fix. No keep-alive for model calls (max_keepalive_connections=0). Each call is seconds of GPU work, so a new TCP connection per request costs nothing measurable. Load went to 16 / 12. Alternatives for larger systems: an L7 proxy, a service mesh, or an inference gateway that routes per request (and can route on KV-cache state).

4. kubectl apply undid the autoscaler

Symptom. After a config change, worker-vlm dropped from 24 to 1 and model-vlm from 2 to 1. KEDA scaled them back up, and the second model server had to reload its weights.

Cause. The manifests set replicas: on Deployments KEDA manages. Every kubectl apply reset the live count to that value.

Fix. Remove replicas from every KEDA-managed Deployment. There's a trap in the fix itself: kubectl apply remembers the previously applied replicas in the last-applied-configuration annotation, and when the field disappears it deletes it, which defaults the count to 1. Strip it from the annotation once first:

kubectl -n docuflow get deploy worker-vlm -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}' \
  | python3 -c "import sys,json; c=json.load(sys.stdin); c['spec'].pop('replicas',None); print(json.dumps(c))" > la.json
kubectl -n docuflow annotate deploy worker-vlm --overwrite kubectl.kubernetes.io/last-applied-configuration="$(cat la.json)"

After that, an apply left every count unchanged (verified before and after).

5. Rolling updates deadlocked on GPU memory

Symptom. After changing vLLM flags, the new pods crash-looped with "Free memory on device (1.2/44.4 GiB) … is less than desired", and the old pods never went away.

Cause. RollingUpdate starts the new pod first, and a shared GPU has no room for it.

Fix. strategy: Recreate for model servers on a shared GPU (Part 5). Prod, with whole GPUs, keeps rolling updates.

6. KEDA couldn't resolve the queue's hostname

Symptom. Every worker ScaledObject showed READY=False; the KEDA operator logged dial tcp: lookup rabbitmq on 10.96.0.10:53: no such host.

Cause. The connection strings used short service names (rabbitmq, db). They resolve inside the docuflow namespace, but KEDA's scalers run in the keda namespace.

Fix. Fully qualified names in every URL a scaler reads: rabbitmq.docuflow.svc.cluster.local.

7. Creation-order race, then a silent backoff

Symptom. Right after the first deploy, the ScaledObjects failed with TriggerAuthentication ... not found. Even after the cause was fixed, KEDA logged nothing for minutes.

Cause. The ScaledObjects reconciled before their TriggerAuthentication existed, and the operator's per-object error backoff then grew to minutes.

Fix. Apply TriggerAuthentications before ScaledObjects, or annotate the ScaledObjects to force a reconcile. In a hurry, kubectl -n keda rollout restart deploy/keda-operator. All five ScaledObjects went READY=True within 30 s.

8. Concurrent vLLM startups miscounted memory

Symptom. Available KV cache memory: -12.92 GiB, and the agent model failed whenever it started at the same time as the others.

Cause. vLLM sizes its KV cache by profiling memory at startup, and other processes loading on the same GPU at the same moment distort the measurement.

Fix. A fixed --kv-cache-memory-bytes per server (Part 5).

9. KEDA scaled the API, and latency got worse

Symptom. Under 96 concurrent queries, KEDA scaled the API from 4 to 8 pods. p50 latency kept rising: 17 s, then 25 s.

Cause. The API wasn't the bottleneck. Each API pod used about 5 millicores. The agent model had 31 of 32 batch slots busy and 64 requests waiting. More API pods only meant more concurrent waiters.

Fix. Scale the component whose own queue is growing. The changes: - the agent model gets more batch slots and a larger KV cache, plus a KEDA trigger on its vLLM queue (in prod) - the agent makes one fewer LLM call per query - ingest backs off when query pressure is high

The API's queries-in-flight trigger is still useful for spreading connections, but its maximum should stay modest.

10. The deployment overwrote the experiment

Symptom. Applying an unrelated fix in the middle of a stress run reset replica counts (failure 4), and a running model server restarted. The run's numbers before and after that moment can't be compared.

Fix. Stop applying manifests during a measured run, or use a dedicated "live patch" path (scripts/mode.sh uses kubectl patch on ScaledObjects and never touches Deployments). Stress-test reports should record every manual intervention with its timestamp.

The pattern

Layer What it limited Failures
app limits concurrency KEDA couldn't see 1
thresholds demand that could never reach the target 2
networking load balancing per connection 3
deployment tooling replica counts, rollout strategy 4, 5, 10
KEDA plumbing DNS, ordering, backoff 6, 7
model server GPU memory budget 8
capacity planning scaling the wrong tier 9

KEDA computed what it was told to compute every single time. The work is in making sure what it reads reflects real demand, and that the capacity it adds can actually be used.

Part 8

Recreate it

From a bare Linux machine with an NVIDIA GPU (driver 570 or newer) to a stress report. Every step is a script or make target in the repository.

1. Host prerequisites

# Docker + the NVIDIA container toolkit (Ubuntu)
sudo apt-get install -y docker.io
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -sL https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
  | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit

# GPUs into kind nodes
sudo nvidia-ctk runtime configure --runtime=docker --set-as-default
sudo nvidia-ctk config --set accept-nvidia-visible-devices-as-volume-mounts=true --in-place
sudo systemctl restart docker

# CLIs: kind 0.24, kubectl, helm 3, kustomize 5 (binaries into ~/.local/bin)

Check that the GPU passes through: docker run --rm -v /dev/null:/var/run/nvidia-container-devices/all ubuntu nvidia-smi -L.

2. Cluster and platform

git clone https://github.com/pramodsarvi/docuflow-systems-lab-.git && cd docuflow-systems-lab-
make cluster-up

scripts/cluster-up.sh does the following: - raises the inotify limits - creates the kind cluster (control plane with ingress ports, GPU worker, CPU worker) - sets up the NVIDIA runtime inside the GPU node, then taints and labels it - installs, through Helm: - metrics-server - ingress-nginx - kube-prometheus-stack - KEDA - the NVIDIA device plugin with time-slicing x6 - the DCGM exporter

At the end the GPU node should show nvidia.com/gpu: 6.

3. Deploy docuflow

make deploy          # builds the image, loads it into kind, applies k8s/overlays/local-gpu, waits for vLLM
make smoke           # 6 pages through VLM reading, then an agent question with a checked citation
make k8s-status      # pods, ScaledObjects, HPAs, GPUs, RabbitMQ queues

The first start downloads about 20 GB of model weights into /var/cache/docuflow-hf; later starts take about a minute. The API is at http://docuflow.localtest.me, Grafana at http://grafana.localtest.me.

Without a GPU, run GPU=0 MONITORING=0 make cluster-up && make deploy OVERLAY=ci-sim. It replaces vLLM with a simulator that has fixed latency and synthetic output. The queue, KEDA and the API behave identically, which is what CI uses.

4. Watch autoscaling

In separate terminals:

watch -n2 kubectl -n docuflow get scaledobject,hpa
watch -n2 "kubectl -n docuflow exec rabbitmq-0 -- rabbitmqctl -q list_queues name messages_ready messages_unacknowledged"
kubectl -n docuflow get pods -w

Then trigger a burst:

curl -XPOST http://docuflow.localtest.me/ingest -H 'content-type: application/json' \
     -d '{"dataset":"synthetic","limit":500,"offset":20000}'

You should see docuflow.vlm jump to about 500 tokens. worker-vlm goes 0 → 1 within ~5 s (KEDA activation), then climbs 3 pods per 10 s to its maximum (HPA scale-up policy). model-vlm adds a replica about a minute later (Prometheus trigger, 30 s stabilisation, ~60 s model load). When the queue drains, workers step down one per 20 s and reach zero 60 s after the last job.

5. Stress test

make stress PAGES=800 C=12                         # run 1 equivalent
.venv/bin/python scripts/stress.py --pages 2000 --offset 2000 \
    --query-steps 8,24,48 --step-seconds 300 --observe-after 420     # ramp + scale-down

Reports land in docs/. For before/after comparisons, change one thing at a time and don't kubectl apply during a run (Part 7, failure 10).

6. Evaluate answer quality

make ragas N=40      # faithfulness, answer relevancy, context precision/recall, judged by the cluster's own models

7. Choose what the GPU is for

make ingest-mode     # pause queries, stop the agent model, page reading gets the whole GPU (~170 pages/min here)
make query-mode      # agent model back, queries open

Cost and capacity notes

  • Worker pods are close to free. They're CPU-light HTTP clients, so let KEDA scale them to zero and to large maxima. Size their maximum against the model servers' batch slots, not against cluster CPU.
  • GPU replicas are where the money is. On one GPU, extra vLLM replicas add batching concurrency but no compute. The second page reader helped mainly because the first one's batch was full, not because the GPU had spare FLOPs.
  • Before buying another GPU, check four things: 1. Are batch slots full while the KV cache is not? Raise --max-num-seqs. 2. Is KV cache reserved but unused? Shrink it and give the memory to the bottleneck. 3. Can ingest and queries take turns (ingest mode overnight, query mode by day)? 4. Are you scaling the tier that's actually queueing?
  • When you do add GPUs, dedicate them by role. Put page reading on one GPU and the agent plus embeddings on another, so ingest bursts can't touch query latency. The prod overlay does this with whole GPUs per model server and KEDA on each server's queue.
